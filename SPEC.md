|---|---|
| **Version** | 1.0 (draft) |
| **Date** | 2026-10-22 |

## 1. Scope

This document specifies the Flipper Remote Keyboard system precisely enough to
implement and test it:

- the Bluetooth LE interface between client and Flipper (§4),
- the key report format (§5),
- the behaviour of the Flipper app (§6),
- the behaviour of the web client (§7).

Requirement IDs in brackets, e.g. [HID-3], refer to [REQUIREMENTS.md](REQUIREMENTS.md).

### 1.1 Conformance

The key words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT** and **MAY** are to
be interpreted as described in RFC 2119.

### 1.2 Normative references

|---|---|

| [HUT] | USB HID Usage Tables 1.4, §10 Keyboard/Keypad Page (0x07) |

### 1.3 Terms

| Term | Meaning |
|---|---|
| **Client** | The web client (§7) running in a browser on a laptop or phone. |
| **Host** | The server the Flipper is plugged into over USB. |
| **Report** | An 8-byte key report (§5). |
| **Usage** | A key's usage ID on the HID Keyboard/Keypad page [HUT]. |
| **Modifier** | One of the 8 keys Left/Right Ctrl, Shift, Alt, GUI. |
| **Current state** | The report the Flipper most recently applied to USB. |

## 2. Architecture

```
┌─────────────────────────────┐          ┌──────────────────────────────────┐          ┌──────┐
│ Client (browser)            │   BLE    │ Flipper app                      │   USB    │ Host │
│                             │  GATT    │                                  │   HID    │      │
│ keydown/keyup ─┐            │  Write   │ GATT write ──▶ validate ──▶ queue│  boot    │      │
│ compose text ──┼─▶ reports ─┼────────▶ │                               │  │ keyboard │      │
│ on-screen keys ┘   + pacing │          │ worker: diff ──▶ furi_hal_hid_* ─┼────────▶ │      │
└─────────────────────────────┘          └──────────────────────────────────┘          └──────┘
```

Data flows one way. The only traffic from the Flipper to the client is
generated by the Bluetooth LE stack itself: advertising, pairing, link-layer
acknowledgements and ATT Write Responses. The application layer defines no
messages from the Flipper to the client.

## 3. Why a custom Bluetooth LE profile

The app MUST NOT use the firmware's built-in `ble_profile_serial`. When that
profile is active, the firmware's `bt` service opens an RPC session on every
connection and installs its own data callback (`bt.c`, `bt_on_gap_event_callback`).
Bytes written by the client would then be fed to the Flipper RPC system, which
gives full control of the Flipper.

Instead, the app defines its own `FuriHalBleProfileTemplate` with a single custom
GATT service (§4.3). The API it needs (`ble_gatt_service_add`,
`ble_gatt_characteristic_init`, `ble_event_dispatcher_register_svc_handler`,
`bt_profile_start`, `bt_keys_storage_set_storage_path`) is exported to apps.

## 4. Bluetooth LE interface

### 4.1 Identifiers

| Item | Value |
|---|---|
| Service UUID | `ff6ad5ee-6d0c-4067-9f0b-25935584962d` |
| Key Report characteristic UUID | `82e449f4-1910-47dd-bb18-a697f0e81a9c` |

These UUIDs identify protocol version 1. An incompatible future version MUST use
new UUIDs. There is no version negotiation.

### 4.2 Advertising and GAP

The app's profile MUST return this `GapConfig` from `get_gap_config`:

| Field | Value |
|---|---|
| `adv_service` | `UUID_TYPE_128`, the service UUID from §4.1 |
| `appearance_char` | `0x0000` (unknown) |
| `bonding_mode` | `true` |
| `pairing_method` | `GapPairingPinCodeShow` |
| `mac_address` | `furi_hal_version_get_ble_mac()` with byte 2 incremented by 2 (wrapping), so it differs from the stock serial profile and the stock HID profile |
| `adv_name` | The Flipper's name (`furi_hal_version_get_name_ptr()`). If it is at most 5 characters: AD type `AD_TYPE_COMPLETE_LOCAL_NAME` + name. Otherwise: `AD_TYPE_SHORTENED_LOCAL_NAME` + the first 5 characters (e.g. `Kalolot` → `Kalol`). Advertising data is limited to 31 bytes, and the stack adds flags (3) and TX power level (3); the 128-bit service UUID takes 18, leaving 7 bytes for the name element. A longer name makes `aci_gap_set_discoverable` fail with `BLE_STATUS_INVALID_PARAMS` (0x92), and the Flipper does not advertise at all (verified on hardware). |
| `conn_param.conn_int_min` | `0x0006` (7.5 ms) |
| `conn_param.conn_int_max` | `0x000C` (15 ms) |
| `conn_param.slave_latency` | `0` |
| `conn_param.supervisor_timeout` | `0` (stack default) |

The short connection interval keeps live-mode latency under the 50 ms target
[NFR-1]. The Flipper is powered by the host's USB port, so the extra power use
does not matter.

### 4.3 GATT service

The service MUST contain exactly one characteristic:

| Property | Value |
|---|---|
| UUID | Key Report characteristic UUID (§4.1) |
| `char_properties` | `CHAR_PROP_WRITE` only (no read, no notify, no indicate, no write-without-response) |
| `security_permissions` | `ATTR_PERMISSION_AUTHEN_WRITE` |
| `gatt_evt_mask` | `GATT_NOTIFY_ATTRIBUTE_WRITE` |
| `is_variable` | `CHAR_VALUE_LEN_VARIABLE` |
| Maximum value length | 16 bytes |

Notes:

- `ATTR_PERMISSION_AUTHEN_WRITE` requires an encrypted link from an authenticated
  (PIN) pairing. A write from an unpaired client is rejected by the stack with an
  ATT error. This error is what makes the client's operating system start pairing
  (§7.2).
- Write-without-response is deliberately not offered. Writes with response are
  ordered, their errors are reported to the client, and they make the OS start
  pairing on the first write.
- 16 bytes fits in the default ATT MTU of 23 (20-byte payload), so no MTU exchange
  and no long (prepared) writes are needed.

### 4.4 Write semantics

Each write to the Key Report characteristic carries one or two reports:

| Value length | Meaning |
|---|---|
| 8 | One report |
| 16 | Two reports, applied in order (bytes 0–7, then 8–15) |
| anything else | Invalid. The Flipper MUST discard the whole write. |

If any report in a write is invalid (§5.3), the Flipper MUST discard the whole
write. The ATT Write Response is sent by the stack regardless; it does not mean
the reports were accepted or typed.

### 4.5 Pairing and bonding

- The app MUST set a dedicated key storage file before starting its profile:
  `bt_keys_storage_set_storage_path(bt, APP_DATA_PATH(".bt_keys"))`. Devices
  paired with the stock firmware (e.g. a phone running the Flipper mobile app)
  therefore cannot send key reports, and pairing with this app does not affect
  them.
- During pairing, the firmware's `bt` service shows the 6-digit PIN on the
  Flipper's screen (`GapEventTypePinCodeShow`). The operator enters it on the
  client. The app does not handle this event itself.
- Bonds persist across app restarts and Flipper reboots.
- To forget bonded clients, the operator holds OK for 3 seconds while the app is
  running (§6.6). The app then calls `bt_forget_bonded_devices(bt)`, which deletes
  the app's key storage file, because it is the active storage path at that time.
  Deleting `apps_data/<appid>/.bt_keys` from the SD card has the same effect.

## 5. Key report format

### 5.1 Layout

A report is the boot keyboard input report from [HID] Appendix B.1:

| Byte | Field | Content |
|---|---|---|
| 0 | Modifiers | Bitmask of held modifiers (§5.2) |
| 1 | Reserved | MUST be `0x00` |
| 2–7 | Keys | Usages of up to 6 held non-modifier keys; `0x00` = empty slot |

### 5.2 Modifier bits

| Bit | Mask | Key | `KEY_MOD_*` in [FZ] |
|---|---|---|---|
| 0 | `0x01` | Left Ctrl | `KEY_MOD_LEFT_CTRL` |
| 1 | `0x02` | Left Shift | `KEY_MOD_LEFT_SHIFT` |
| 2 | `0x04` | Left Alt | `KEY_MOD_LEFT_ALT` |
| 3 | `0x08` | Left GUI (Win / Cmd) | `KEY_MOD_LEFT_GUI` |
| 4 | `0x10` | Right Ctrl | `KEY_MOD_RIGHT_CTRL` |
| 5 | `0x20` | Right Shift | `KEY_MOD_RIGHT_SHIFT` |
| 6 | `0x40` | Right Alt (AltGr) | `KEY_MOD_RIGHT_ALT` |
| 7 | `0x80` | Right GUI | `KEY_MOD_RIGHT_GUI` |

`KEY_MOD_*` values in [FZ] are these masks shifted left by 8, i.e.
`KEY_MOD_x == mask << 8`.

### 5.3 Validity rules

A report is valid if and only if all of these hold:

1. Byte 1 is `0x00`.
2. Every non-zero byte in 2–7 is in `0x04`–`0xA4` (the range [HUT] defines for
   keyboard keys; `0x01`–`0x03` are error codes and MUST NOT be sent).
3. No usage in `0xE0`–`0xE7` appears in bytes 2–7. Modifiers are sent only in
   byte 0.
4. No non-zero usage appears more than once in bytes 2–7.

The position of a usage within bytes 2–7 has no meaning. Empty slots MAY appear
anywhere.

### 5.4 State semantics

- A report describes the **complete** set of keys held at that moment. It is not
  a delta.
- An all-zero report (`00 00 00 00 00 00 00 00`) means "nothing held".
- A key is *pressed* by sending a report that contains it, and *released* by
  sending a report that does not.
- Typing the same character twice requires a report without the key in between.

### 5.5 Examples

| Action | Reports (hex) |
|---|---|
| Type `a` | `00 00 04 00 00 00 00 00`, `00 00 00 00 00 00 00 00` |
| Type `A` (US) | `02 00 04 00 00 00 00 00`, `00 00 00 00 00 00 00 00` |
| Ctrl+Alt+Del | `05 00 4C 00 00 00 00 00`, `00 00 00 00 00 00 00 00` |
| Ctrl+Alt+F2 | `05 00 3B 00 00 00 00 00`, `00 00 00 00 00 00 00 00` |
| Hold Shift, press and release `x`, release Shift | `02 00 00 00 00 00 00 00`, `02 00 1B 00 00 00 00 00`, `02 00 00 00 00 00 00 00`, `00 00 00 00 00 00 00 00` |

## 6. Flipper app

### 6.1 Manifest

| Field | Value |
|---|---|
| `appid` | `remote_keyboard` |
| `name` | `Remote Keyboard` |
| `apptype` | `FlipperAppType.EXTERNAL` |
| `fap_category` | `USB` |
| Build tool | `ufbt` |

### 6.2 Startup sequence

The app MUST perform these steps in order:

0. Show the main screen (§6.6) and start the worker thread (§6.3.2). The worker
   starts first so that no callback can signal it before it exists.
1. Save the current USB interface: `usb_prev = furi_hal_usb_get_config()`.
2. `furi_hal_usb_unlock()`, then `furi_hal_usb_set_config(&usb_hid, NULL)`. If this
   fails, show an error and exit without touching Bluetooth.
3. Register a HID state callback with `furi_hal_hid_set_state_callback` (§6.5).
4. Open `RECORD_BT`. Call `bt_disconnect(bt)` and wait 200 ms.
5. `bt_keys_storage_set_storage_path(bt, APP_DATA_PATH(".bt_keys"))`.
6. `profile = bt_profile_start(bt, &remote_keyboard_profile, NULL)`, then set the
   profile's receive callback. If it returns `NULL`, restore the default key path
   and USB config, show an error and exit.
7. `furi_hal_bt_start_advertising()`.
8. Register a status callback with `bt_set_status_changed_callback` (§6.4).

### 6.3 Receive and apply

#### 6.3.1 Receive path (Bluetooth thread)

On `ACI_GATT_ATTRIBUTE_MODIFIED_VSEVT_CODE` for the Key Report value handle
(characteristic handle + 1), the service event handler MUST:

1. Check the length and every report against §4.4 and §5.3. If any check fails,
   discard the whole write.
2. Put each report, in order, into a `FuriMessageQueue` of 8-byte items with
   capacity **512**, using timeout 0. If the queue is full, drop this report and
   any later reports in the write.
3. Return `BleEventAckFlowEnable`.

The handler MUST NOT call `furi_hal_hid_*` or block.

#### 6.3.2 Apply path (worker thread)

The worker keeps `current`, the last applied report (initially all zero). For
each report `next` taken from the queue, it MUST:

1. Compute the change from `current` to `next` and call the firmware in this
   order, so modifiers are held before keys go down and after keys come up:
   1. `furi_hal_hid_kb_release(u)` for each usage `u` in `current` but not in `next`.
   2. `furi_hal_hid_kb_release(m << 8)` for each modifier bit `m` set in `current`
      but not in `next`.
   3. `furi_hal_hid_kb_press(m << 8)` for each modifier bit `m` set in `next` but
      not in `current`.
   4. `furi_hal_hid_kb_press(u)` for each usage `u` in `next` but not in `current`.
2. Set `current = next`.
3. If any call in step 1 returned `false` while `furi_hal_hid_is_connected()` is
   true, re-send the current state by calling
   `furi_hal_hid_kb_press(HID_KEYBOARD_NONE)` (which changes nothing and sends
   the report again) until it returns `true` or 50 ms have passed.
4. Wait until at least **8 ms** have passed since step 1 began, then take the
   next report.

Each firmware call sends one USB report, so the host sees each change in order
[HID-3]. Step 4 makes sure every state lasts long enough for slow BIOS input
handlers to see it.

If `next` equals `current`, step 1 makes no calls. This is not an error.

### 6.4 Client disconnect

When the status callback reports a status other than `BtStatusConnected` after
having been connected, the app MUST:

1. Empty the queue (`furi_message_queue_reset`).
2. Call `furi_hal_hid_kb_release_all()` and set `current` to all zero [HID-6].

Advertising restarts automatically, so a client can reconnect without user
action [BLE-3].

### 6.5 USB host connect and disconnect

When the HID state callback reports that the host disconnected (e.g. the server
rebooted or powered off), the app MUST empty the queue and set `current` to all
zero. Reports received while the host is disconnected are dropped by the worker.
The app MUST keep running and keep its Bluetooth connection, so typing resumes as
soon as the host enumerates the keyboard again [NFR-6].

### 6.6 User interface

The app shows one static screen, for example:

```
 Remote Keyboard
 Pair or connect from
 the web client.
 Hold OK: forget devices
 Back: exit
```

| Input | Action |
|---|---|
| Back (short) | Exit (§6.7) [APP-2] |
| OK held ≥ 3 s | `bt_disconnect`, wait 200 ms, `furi_hal_bt_stop_advertising`, `bt_forget_bonded_devices`, `furi_hal_bt_start_advertising` (the stock HID app's sequence). Show "Paired devices forgotten" for 2 s, then the main screen again. |
| Other | Ignored |

The screen MUST NOT show connection state, received data or any other runtime
information [APP-1]. The PIN screen during pairing is drawn by the firmware.

### 6.7 Exit sequence

The app MUST perform these steps in order:

1. Stop the worker thread and empty the queue.
2. `furi_hal_hid_kb_release_all()`.
3. `bt_set_status_changed_callback(bt, NULL, NULL)`.
4. `bt_disconnect(bt)` and wait 200 ms.
5. `bt_keys_storage_set_default_path(bt)`.
6. `bt_profile_restore_default(bt)`.
7. `furi_hal_hid_set_state_callback(NULL, NULL)`.
8. `furi_hal_usb_set_config(usb_prev, NULL)` [HID-1].
9. Close `RECORD_BT` and free resources.

### 6.8 Restrictions

- The app MUST NOT write received data to the SD card, logs or the screen. Log
  messages MUST NOT include report contents [APP-4].
- The app MUST NOT have settings or read a config file [APP-3].
- The app MUST NOT send anything to the client: no notifications, indications
  or readable characteristics.

## 7. Web client

### 7.1 Platform and hosting

- The client is a single static page: one HTML file plus optional local JS, CSS
  and layout JSON files. It has no backend [WEB-1].
- It MUST be served over HTTPS, or from `http://localhost` during development.
- It MUST NOT load third-party scripts, fonts or analytics. The page SHOULD send
  a Content Security Policy with `default-src 'self'` and `connect-src 'self'`
  [SEC-5]. `connect-src 'self'` (not `'none'`) is needed to fetch the layout
  files from the page's own origin; requests to any other origin stay blocked.
  GitHub Pages cannot set headers, so the policy is set with a `<meta>` tag.
- Feature detection: if `navigator.bluetooth` is undefined, or
  `await navigator.bluetooth.getAvailability()` is `false`, the page MUST show a
  message naming the supported browsers (Chrome or Edge on desktop, Chrome on
  Android, Bluefy on iOS) and MUST NOT show the connect button [WEB-13].

### 7.2 Connecting and pairing

1. On a button press (a user gesture is required by [WBT]), call
   `navigator.bluetooth.requestDevice({ filters: [{ services: [SERVICE_UUID] }] })`.
2. `device.gatt.connect()`, `getPrimaryService(SERVICE_UUID)`,
   `getCharacteristic(KEY_REPORT_UUID)`.
3. Write one all-zero report with `writeValueWithResponse`. If the client is not
   bonded, the Flipper rejects this write (§4.3) and the OS starts pairing. The
   Flipper shows a PIN, and the OS asks the operator to enter it. If the first
   write fails, the client MUST retry it once after pairing completes, or after
   3 seconds.
4. When the zero report is written successfully, the client is ready.

Pairing is a one-time step per client device. Web Bluetooth has no pairing API.
In practice the Flipper's GAP layer requests security as soon as a client
connects ("Slave security initiated"), so the OS starts pairing on connect; the
ATT authentication error on the first write is a fallback. Verified on macOS with
CoreBluetooth (via `bleak`): the PIN prompt appeared on connect, and the first
write completed by itself once the PIN was entered. Also verified on iOS with
Bluefy and the web client.

The client MUST listen for `gattserverdisconnected`. On disconnect it MUST empty
its send queue, show "Disconnected" and offer a Reconnect button that calls
`device.gatt.connect()` on the same `BluetoothDevice` and repeats steps 2–4
[WEB-12].

### 7.3 Send queue

Web Bluetooth allows only one GATT operation at a time. The client MUST send all
reports through a single FIFO queue:

- Writes MUST use `writeValueWithResponse` and MUST be awaited one at a time.
- If two or more reports are waiting, the client MAY combine the first two into
  one 16-byte write (§4.4).
- The client MUST NOT drop, merge or reorder reports. (Merging states would lose
  quick taps whose press and release are both queued.)
- If a write fails while connected, the client MUST retry it once, then empty the
  queue and send an all-zero report.

### 7.4 Live mode

Live mode forwards physical key presses from the client's keyboard [WEB-4].

**State.** The client keeps a modifier bitmask and an ordered list of held
usages (at most 6).

**Capture.** Live mode is active while a dedicated capture element has focus. On
`keydown` and `keyup` on that element the client MUST:

1. Ignore the event if `event.isComposing` is true, or `event.code` is empty, is
   `"Unidentified"`, or is not in Appendix A.
2. Ignore `keydown` events with `event.repeat === true`. The host does its own
   auto-repeat while the key is held.
3. Call `event.preventDefault()`.
4. Update the state from `event.code` using Appendix A: set or clear the
   modifier bit, or add or remove the usage. A 7th simultaneous non-modifier key
   is ignored.
5. If the state changed, build a report and queue it.

**Releasing.** The client MUST queue an all-zero report and clear its state when
any of these happen [WEB-6]:

- the capture element fires `blur`,
- `document.visibilityState` becomes `"hidden"`,
- live mode is turned off,
- the client disconnects (state only; nothing can be sent).

**Platform quirks.** The client MUST handle these:

| Platform | Quirk | Handling |
|---|---|---|
| macOS | Chrome fires `keydown` for CapsLock when it turns on and `keyup` when it turns off, not on physical press and release. | On either event, queue a press and a release of CapsLock (`0x39`). |
| macOS | While Cmd is held, `keyup` is not fired for other keys. | When `MetaLeft`/`MetaRight` is released, also release every non-modifier key pressed while it was held. |
| Windows | AltGr fires a fake `ControlLeft` `keydown` immediately before `AltRight`. | If an `AltRight` `keydown` arrives with the same `event.timeStamp` (±2 ms) as a `ControlLeft` `keydown`, remove the Left Ctrl bit and send the corrected report. The matching `ControlLeft` `keyup` is ignored. |

#### 7.4.1 Live typing on touch devices

Phone on-screen keyboards produce characters, not physical keys, and open only
for a real text field. On devices whose primary pointer is coarse
(`matchMedia("(pointer: coarse)")`), live mode MUST show a text input instead of
the capture area:

- After every `input` event (and `compositionend`), the client compares the
  field's value with its previous value, assuming edits at the end. Removed
  characters are sent as Backspace taps; added characters are typed with the
  selected layout, as in compose mode (§7.6). This covers autocorrect, word
  suggestions and Android composition, which edit whole words at once.
- The field is kept filled with invisible padding (zero-width spaces), so
  Backspace always fires an `input` event, and is reset to the padding after
  each change (not during composition).
- `keydown` with `key === "Enter"` sends Enter.
- Once-modifiers (§7.5) apply to the next typed character.
- Characters missing from the layout are skipped; the page says how many, but
  never echoes the text, which may be a password.

**Keyboard Lock.** On desktop Chrome and Edge, the client SHOULD offer a
fullscreen button that calls `element.requestFullscreen()` and then
`navigator.keyboard.lock()`. This lets the page capture combinations the
browser would otherwise take, such as Ctrl+W, Ctrl+T, Alt+Tab and the Windows key.

### 7.5 On-screen keys

The client MUST show on-screen buttons for keys and combinations that cannot be
captured, or that a phone keyboard lacks [WEB-6, WEB-7]:

| Group | Buttons |
|---|---|
| Combinations | Ctrl+Alt+Del, Alt+Tab, Alt+F4, GUI, Ctrl+Alt+F1 … Ctrl+Alt+F7 |
| Keys | Esc, Tab, Enter, Backspace, Delete, Insert, Home, End, PgUp, PgDn, arrows, F1–F12, Print Screen |
| Modifiers | Ctrl, Shift, Alt, AltGr, GUI |

- Every group, the modifiers included, is a collapsible section, closed by
  default. The client remembers each section's open state in `localStorage`.
- A key or combination button queues one report with all its keys, then an
  all-zero report.
- A modifier button cycles through three modes on each tap:
  - **Off.**
  - **Once:** added to the next key press (on-screen key, or a character typed
    on a touch device), then back to Off. Combined with any key button, this
    gives arbitrary combinations.
  - **Held:** pressed on the server immediately and kept pressed until tapped
    again: the client ORs the held modifiers into byte 0 of *every* report it
    queues, from every mode, including all-zero reports. Tapping it again
    releases it at once. Example: hold Alt, tap Tab repeatedly, release Alt
    (Alt+Tab window switching).
- The Modifiers section heading shows the active modifiers and their modes, so
  a held modifier is visible while the section is collapsed.
- Tapping a key or section heading while the live typing area has focus MUST
  NOT move focus away (cancel `pointerdown`), so the phone keyboard stays open
  and desktop live typing combines with held modifiers.
- Arrow buttons SHOULD repeat while held (first repeat after 400 ms, then every
  50 ms), each repeat sending a press and a release.

### 7.6 Compose mode

Compose mode types text by converting characters to key presses [WEB-8].

**Layout tables.** A layout table is a JSON file:

```json
{
  "id": "us",
  "name": "English (US)",
  "map": {
    "a": [[0, 4]],
    "A": [[2, 4]],
    "\n": [[0, 40]]
  }
}
```

- `map` keys are single Unicode characters (NFC).
- Each value is a list of strokes `[modifiers, usage]`, typed in order. Characters
  that need a dead key take two or more strokes.
- `usage` MUST satisfy §5.3. `modifiers` is a bitmask as in §5.2.

The client MUST include the US table (Appendix B) [WEB-9]. Further tables MAY be
added as files with no code changes. The selected layout is stored in
`localStorage`; if storage is unavailable, the default is `us`.

**Algorithm.** When the operator presses Send, the client MUST:

1. Normalize the text to NFC and replace `\r\n` and `\r` with `\n`.
2. For each character, look it up in the table. If it is missing, skip it and
   increase a skipped-characters counter.
3. For each stroke, queue `[modifiers, 0, usage, 0, 0, 0, 0, 0]` and then the
   all-zero report.
4. Wait the character interval *D* between characters (between the last report
   of one character and the first report of the next).
5. When done, show "Sent N characters, skipped M". This is local information,
   not feedback from the Flipper.

*D* defaults to 20 ms and can be set from 16 to 1000 ms [WEB-11]. 16 ms is the
lowest value that keeps up with the Flipper's 8 ms per report (two reports per
character).

**Stop.** A Stop button MUST empty the send queue and queue an all-zero report.

**Password field** [WEB-10]: an `<input type="password" autocomplete="off">`
with its own Send button. It is typed with the same algorithm. Its value MUST be
cleared right after it is queued, and MUST NOT be stored, logged or put in
history. A "Press Enter after the password" checkbox, on by default, appends
Enter (e.g. for a disk-encryption prompt).

### 7.7 Local status

The client MAY show only information it knows locally: connection state,
selected layout, compose progress and the skipped-character count. It MUST NOT
claim that keys reached the host.

## 9. Security considerations

- **Who can type.** Only clients bonded to the app through an authenticated
  (PIN) pairing can write key reports (§4.3, §4.5). The PIN is shown only on
  the Flipper's screen, so pairing requires physical access to the Flipper
  [SEC-1, SEC-2].
- **Confidentiality.** All writes go over an encrypted link. Passwords typed in
  compose or live mode are not exposed over the air [SEC-4].
- **Isolation from the Flipper's RPC.** Using a custom profile (§3) means key
  reports can never reach the Flipper RPC system. The separate key storage means
  phones bonded for the Flipper mobile app cannot type.
- **Revocation.** Hold OK for 3 seconds in the app, or delete the key file
  (§4.5) [SEC-3].
- **Client.** The page makes no network requests after loading (§7.1), and
  password values are never stored (§7.6) [SEC-5].
- **Residual risk.** A bonded client device that is lost or stolen can type into
  any server the Flipper is plugged into while the app is running. Revoke bonds
  if that happens.

The acceptance criteria in [REQUIREMENTS.md](REQUIREMENTS.md) §10 apply. In

a scripted client (e.g. Python `bleak`):

| # | Test | Expected |
|---|---|---|
| T1 | Write 0, 7, 9, 15 and 24 bytes | All discarded; host sees nothing |
| T2 | Write a report with byte 1 = `0x01` | Discarded |
| T3 | Write a report with usage `0xE1` in byte 2 | Discarded |
| T4 | Write a report with the same usage in bytes 2 and 3 | Discarded |

| T10 | Unplug USB while connected, plug it back in, send `a` | `a` typed; Bluetooth stayed connected |
